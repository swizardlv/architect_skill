# 架构硬约束与前置假设规约 (Constraints & Assumptions)

> **架构视角**: 既成事实与不可逾越的边界 (The Inviolable Givens & Boundaries)  
> **核心使命**: 识别架构技能工具链外部施加的开发环境、依赖安全、跨平台兼容与物理沙箱边界，将其确立为工具链架构推导的硬性围栏，严禁将个人技术偏好伪装成约束。

---

## 1. 架构硬约束三大范畴全景表 (Constraints Master Table)

### 1.1 业务与组织约束 (Business & Organizational Constraints, BC)
| 标识 | 约束维度 | 既成事实与硬性规约 (Givens) | 违反后果 (Impact of Violation) | 驱动的架构关注点 (Architectural Impact) |
| :--- | :--- | :--- | :--- | :--- |
| **BC-01** | **交付与单测全绿** | 每次提交前必须执行并通过 `npm run compile && npm run lint && npm test` | 破坏持续集成稳定性，禁止合入远程分支 | 自动化集成脚本与严格的单测断言防护 |
| **BC-02** | **纯净架构库资产** | 核心代码库 `architect_skill` 纯洁，严禁混入具体业务案例 | 导致核心抽象被业务污染，无法作为通用技能复用 | 建立独立的外部测试案例工作区目录架构 |
| **BC-03** | **中文沟通与文档** | 所有架构文档、思考链与交互沟通必须以中文呈现 | 违背团队组织与评审标准 | 全链路中文文档模板与代码注释规范 |

### 1.2 技术与遗留资产约束 (Technical & Legacy Constraints, TC)
| 标识 | 约束维度 | 既成事实与硬性规约 (Givens) | 违反后果 (Impact of Violation) | 驱动的架构关注点 (Architectural Impact) |
| :--- | :--- | :--- | :--- | :--- |
| **TC-01** | **语言与运行时环境** | 核心逻辑采用 Python 3.10+ 标准库，支持标准 POSIX Shell (zsh/bash) 与 Node.js 18+ | 导致环境兼容性破坏，在受限 CI 容器中无法运行 | 最小化外部重型依赖，使用轻量原生库实现 |
| **TC-02** | **依赖开源许可合规** | 严禁引入带有 GPL 传染性开源协议的外部第三方依赖包 | 产生知识产权合规风险 | 严格采用 MIT / Apache 2.0 兼容许可依赖 |
| **TC-03** | **状态文件原子操作** | 状态机进度与快照持久化必须采用临时文件原子重命名（Atomic Rename） | 进程中断时导致 JSON 损坏，无法恢复会话 | `StateManager` 本地原子落盘机制与锁防护 |

### 1.3 法律、合规与监管红线 (Legal & Compliance Constraints, LC)
| 标识 | 约束维度 | 既成事实与硬性规约 (Givens) | 违反后果 (Impact of Violation) | 驱动的架构关注点 (Architectural Impact) |
| :--- | :--- | :--- | :--- | :--- |
| **LC-01** | **数据主权与隐私保护** | 严禁在未经脱敏的情况下向公网或大模型 API 上传用户敏感凭据与私有代码 | 违反企业安全合规红线与数据主权法 | 设立前置扫描拦截器，阻断敏感密钥落盘 |
| **LC-02** | **执行沙箱隔离** | 外部子进程执行必须设定严格硬超时（Hard Timeout ≤ 30s），严禁无限制卡死 | 产生失控死循环或资源耗尽 | 子进程包装器强制发送 SIGKILL 并回收系统资源 |

## 2. 约束与技术决策区分检验 (Constraint vs. Decision Test)
严密排查是否存在把“个人技术偏好”误写为“硬性约束”的反模式：

| 候选约束条目 | 检验提问：若打破该限制，公司会面临违法、严重业务停摆还是只是换个技术实现？ | 检验裁定 | 处置策略 |
| :--- | :--- | :--- | :--- |
| “看板生成必须使用某一特定前端框架渲染” | 换用原生静态 HTML+JS 依然能够高质量呈现图元，无环境硬伤 | **技术决策 (Decision)** | **移出约束清单**，放入 ADR 论证其轻量化优势 |
| “提交前必须执行编译与单测全通过” | 打破该限制将导致脏代码流入生产，项目直接构建失败停摆 | **绝对硬约束 (Constraint)** | **确立为 BC-01 组织硬约束**，作为 CI 唯一放行门禁 |
| “核心代码库严禁混入具体业务案例代码” | 混入业务代码将导致技能失去通用性架构工具属性 | **绝对硬约束 (Constraint)** | **确立为 BC-02 架构纯净约束**，指导测试工作区分离 |

## 3. 核心前置假设与失效触发机制 (Assumptions & Invalidation Triggers)

| 假设编号 | 假设内容与上下文 | 设立依据 | 失效触发条件 (Invalidation Trigger) | 失效后系统应对与架构演进方案 |
| :--- | :--- | :--- | :--- | :--- |
| **ASM-01** | 宿主环境具备对工作区目录的标准读写文件系统权限 | 正常开发机与 CI 容器环境 | 部署到完全只读的不可变文件系统环境中 | 降级为基于内存虚拟文件系统 (VFS) 暂存产物，输出至标准输出 |
| **ASM-02** | 大语言模型在遵循结构化 Prompt 时能够稳定输出合法 JSON / Markdown | 当前主流前沿认知推理模型能力 | 模型退化或高频产生损坏截断格式 | 激活内置重试与负向提示词自愈校验机制，必要时触发人工打回 |
| **ASM-03** | 单元测试环境具备 Python 与 pytest 运行套件 | 标准 Node/Python 开发套件 | 遇到缺失 pytest 的最小精简镜像 | 自动回退为基于 Python 内置 `unittest` 模块运行核心守卫断言 |
