## 1. 背景与驱动力 (Context & Forces / Drivers)

平台正在构建用于自动化分析、推导与修复复杂工程代码与架构图纸的 Agent 智能体。在长任务与多步推理执行过程中，当初次生成的方案或修复补丁未能通过静态门禁（如语法编译、JSON Schema 校验或自动化测试）时，系统会进入自我反思与重试循环。

在实测与 PoC 演练中暴露了两个破坏性瓶颈：
1. **Token 成本呈指数膨胀 (驱动力 ARC-AI-03)**:
   - 现有的简单全量会话追加模式（将前置步骤的长达数百行堆栈报错、修改后的全量代码文件反复追加到提示词中），导致在第 3 轮重试时上下文暴增至 64k+ Token。
   - 单任务模型推理成本突破 $0.25，严重违背单次任务成本控制在 $0.04 以内的经济学红线。
2. **注意力稀释与“土拨鼠之日”死循环 (驱动力 ARC-AI-01)**:
   - 评测基准数据显示，由于上下文充斥冗余日志噪音，模型注意力机制被严重稀释。在 38% 的多轮重试用例中，模型反复提出已被前序步骤证明失败的同一种修复思路，陷入自我纠缠的死循环。

## 2. 考量的备选方案 (Options Considered)

### 2.1 候选方案客观对比矩阵 (Trade-off Comparison Matrix)

| 评估维度 (Evaluation Criteria) | 备选方案 A: 滑动窗口截断 (Sliding Window) | 备选方案 B: 纯 LLM 滚动摘要 (LLM Summarization) | 备选方案 C (采纳方案): 确定性差分修剪 + 显式负向假设账本 |
| :--- | :--- | :--- | :--- |
| **核心范式与机制** | 仅保留最近 1 轮工具输出，历史直接截断 | 每轮结束后额外调用轻量模型压缩历史记录 | 确定性脚本提取 Stack Trace 关键行 + `git diff` 差分 + 结构化负向账本 |
| **确定性锚点 (外围防护)** | 弱 (丢失历史上下文，缺乏硬约束) | 弱 (二次概率模型，存在二次幻觉风险) | **强 (基于确定性 AST 与状态机硬编码防重指纹)** |
| **评测基准准确率 (Pass@1)** | 37% (严重丧失长期记忆，成功率跌破底线) | 68% (摘要丢失精准行号，定位产生偏差) | **82% (信息精准无衰减，成功率最高)** |
| **重复错误发生率 (Evals-v2.1)** | 45% (频繁重复尝试第 1 轮证伪方案) | 16% (部分摘要丢失关键证伪逻辑) | **2.8% (负向账本强拦截，基本杜绝重复犯错)** |
| **Token 消耗 / 单任务成本**| 极低 (单任务 ~$0.015) | 中高 (额外模型调用，单任务 ~$0.075) | **优 (每轮增量 < 1k Token，单任务成本 $0.028)** |
| **首字流式时延 (TTFT)** | 快 (无需任何额外计算) | 显著变慢 (额外模型摘要增加 2.0s~3.5s) | **快 (本地差分与修剪耗时 < 30ms)** |
| **可观测性与黑盒排障成本** | 极高 (历史断代，无法排查最初根因) | 中等 (需要人工核对摘要与真实日志偏差) | **低 (结构化负向账本与 Patch 易于阅读回溯)** |
| **模型/Prompt 锁定风险** | 低 (无特殊格式依赖) | 高 (依赖特定摘要 Prompt 调优) | **低 (标准 Unified Diff 与紧凑 JSON 格式，通用适配)** |
| **综合裁决** | **否决 (Rejected)** | **否决 (Rejected)** | **采纳 (Accepted)** |

### 2.2 各备选方案详细推演

#### 备选方案 A: 简单的滑动窗口截断 (Sliding Window Truncation)
- **核心设想**: 仅保留最近 1 轮的工具调用输出与思考内容，更早的历史消息直接移出上下文。
- **优势**: 工程实现极其轻量，Token 增长线性受限。
- **劣势与硬伤**: 导致 Agent 丢失前序已执行的推导假设，在第 3 轮重试时频繁重复尝试第 1 轮已被推翻的假设。在 `evals-dataset-v2.1` 上的解决率从 75% 剧烈滑落至 37%。
- **否决根因**: 严重违背 ARC-AI-01 任务达成率核心指标。

#### 备选方案 B: 基于纯 LLM 的滚动总结压缩 (LLM-based Summarization)
- **核心设想**: 每轮循环结束后，异步触发轻量大模型对历史错误与推理轨迹生成精简的自然语言摘要。
- **优势**: 能够压缩文本体积，维持自然语言上下文连续。
- **劣势与硬伤**: 引入二次网络往返推理，大幅恶化单步时延（增加 2~3.5 秒）；更为严重的是，自然语言摘要容易产生幻觉，遗漏报错调用栈中的精准行号或局部变量名。
- **否决根因**: 推理时延超标且存在摘要幻觉导致代码误改，单任务总成本未达标。

#### 备选方案 C (采纳方案): 确定性状态差分修剪 + 显式负向假设账本 (Diff-Pruning & Negative Ledger Pattern)
- **核心设想**:
  1. **堆栈精准裁剪**: 拒绝回传全量几百行的原始 Stack Trace，采用确定性脚本仅提取核心异常类型、核心调用行与直接相关的代码锚点；
  2. **代码状态差分**: 严禁全量回传修改后的文件，仅向模型提供基于基准代码的标准 `git diff` 统一补丁视图；
  3. **负向假设结构化注记**: 由状态机维护结构化 `NegativeHypothesis` 账本（记录：`{attempt: 1, strategy: "类型断言强化", failure_reason: "引发下游空指针"}`），以极度紧凑的格式注入系统提示词。
- **优势**: 抑制 Token 膨胀，每轮增量稳定在 1k 以内；从外围杜绝重复错误，提升模型注意力聚合度；纯确定性算法，零二次模型推理开销。
- **代价**: 需在 CM 中构建专门的修剪中间件与差异提取器。

## 3. 决策结果与裁决理由 (Decision Outcome & Rationale)

我们决定采纳 **备选方案 C: 确定性状态差分修剪 + 显式负向假设账本模式** 作为重试循环上下文治理的标准实现。

### 关键裁决依据
1. **落实确定性锚点原则 (Deterministic Anchor Rule)**:
   坚决打破依赖大模型自觉控制上下文的幻想。方案 C 依靠外围确定性工程代码过滤无用信息，并由外部状态机记录“负向失败账本”，从物理机制上消除模型陷入自旋死循环的根因。
2. **严守 Token 单位经济学与流式时延**:
   在标准评测集验证下，重试 3 轮以内的平均任务 Token 消耗下降 68%，成本从 $0.25 压缩至 $0.028，符合 ARC-AI-03 规定；本地修剪耗时小于 30ms，保障流式响应时效。
3. **避免供应商锁定与具备模型中立性 (Vendor Neutrality)**:
   输入输出采用标准的 Unified Diff 与 JSON 键值对，无需对特定厂商大模型调优专用 System Prompt，具备从闭源旗舰模型平滑切换至开源私有化模型的能力。

## 4. 影响、代价与工程缓解策略 (Consequences, Trade-offs & Mitigations)

### 4.1 正向收益 (Positive Consequences)
- **任务达成率提升**: 在 `evals-dataset-v2.1` 黄金测试集上，一次性解决率 (Pass@1) 达到 82%，且多轮重复错误率控制在 2.8% 以下。
- **成本与上下文优化**: 会话上下文膨胀率降低 75%，单次平均推理成本下降至 $0.028，达成业务指标。

### 4.2 负面代价与技术债务 (Negative Consequences & Trade-offs)
- **代价 1 (CM 组件复杂度增加)**: 必须在架构组件模型中新增 `COMP-CTX (上下文优化与修剪中间件)`，需要投入约 8 人天的工程开发量。
- **代价 2 (多技术栈语法适配)**: 报错堆栈提取与差分视图生成需适配不同编程语言的异常打印格式，存在一定的初期适配负担。
- **代价 3 (黑盒可观测性与审计排障成本)**: 上下文经过工程修剪后，如果模型仍然推理错误，工程师在事后复盘时无法直接从模型输入中看到原始全量日志，需要检索原始存档。

### 4.3 工程缓解与补偿策略 (Mitigations & Compensating Controls)
针对上述每一项代价，设立专门的工程防线：
1. **针对 [代价 1 - 组件复杂度] 的缓解**:
   将 `COMP-CTX` 设计为独立的轻量无状态函数库，定义严格的输入输出接口，与状态调度核心解耦，便于独立单元测试。
2. **针对 [代价 2 - 多语言适配] 的缓解**:
   优先针对主流语言（Python, TypeScript, Go）实现精准 AST/正则解析器；对于未涵盖的长尾语言，提供保守的基础头尾截断规则保底。
3. **针对 [代价 3 - 黑盒排障追溯] 的缓解**:
   在执行修剪的同时，将**原始全量输入上下文与修剪后上下文**同时写入本地只追加式审计快照表（Audit Trace Snapshot），排障时支持单步快照重放对比。
