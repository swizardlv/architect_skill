## 1. 背景与驱动力 (Context & Forces / Drivers)

在复杂软件架构的设计过程中，若允许大语言模型自由发挥、跳步推演或无约束协同，极易产生“跳过非功能性需求直接写代码”、“未定义边界契约直接生成物理模型”、“产出物缺乏一致性校验”等问题。
系统需要一套既能引导智能体自主推进、又能施加严密工业级门禁（Gatekeeper）与人类干预回退（HITL）的生命周期调度核心。

### 核心矛盾焦点 (Core Conflict)
1. **智能体自主生成效率 vs 工业级架构工程严谨性**: 架构设计必须经历严格的“需求澄清 -> 概念抽象 -> 逻辑解耦 -> 物理运行 -> 决策取舍 -> 交付评估”单向递进链路。
2. **长会话上下文易丢 vs 复杂多步任务断点可恢复性**: 必须支持随时中断、状态落地并在新会话中无缝恢复。

## 2. 考量的备选方案 (Options Considered)

### 2.1 候选方案客观对比矩阵 (Trade-off Comparison Matrix)

| 评估维度 (Evaluation Criteria) | 方案 A: 纯提示词网状自主智能体 | 方案 B: 静态线性 Shell 脚本 | 方案 C (采纳方案): 确定性有限状态机 (FSM) |
| :--- | :--- | :--- | :--- |
| **执行路径确定性** | 极低 (概率性跳步与循环) | 较高 (严格从头到尾) | **100% 状态机驱动，合法跳转受限** |
| **确定性锚点 (外围防护)** | 弱 (单点信任大模型自觉性) | 中 (基础进程 Exit Code) | **强 (外部 Python 状态机强约束，代码级硬门禁)** |
| **基准测试规范通过率 (Evals)** | 42% (频繁跳步或遗漏核心产物) | 65% (无法处理驳回返工循环) | **96% (严格依照规范产出全部交付工件)** |
| **断点恢复能力 (RTO/RPO)** | 差 (依赖窗口重注入，RPO 无法保证) | 差 (无细粒度状态快照) | **优 (原生支持原子写入 JSON 快照，RTO < 50ms)** |
| **门禁拦截能力 (Gatekeeper)**| 弱 (Prompt 容易被越狱或忽视) | 中等 (基于简单 exit code) | **强类型硬门禁，产物不达标禁止跳转** |
| **模型/Prompt 锁定逆转成本** | 极高 (依赖特定模型长上下文跟随能力) | 零 (纯脚本与大模型解耦) | **低 (状态机外置于 Python 代码，模型可任意替换)** |
| **可观测性与黑盒排障成本** | 极高 (状态散落在非结构化对话中) | 低 (控制台输出日志) | **优 (结构化状态机可视化映射与图元同步)** |
| **综合裁定** | **否决 (Rejected)** | **否决 (Rejected)** | **采纳 (Accepted)** |

## 2.2 各备选方案详细推演

#### 方案 A: 纯提示词驱动的网状自主智能体 (Autonomous Multi-Agent Swarm)
- **核心设想**: 依赖 System Prompt 引导多个 Agent 互相交流自发推进设计。
- **优势 (Pros)**: 灵活性高，前期开发轻便。
- **劣势与硬伤 (Cons)**: 执行链路非确定；Agent 常在未收敛需求前直接臆造物理实现；缺乏不可逾越的机器门禁。
- **被否决根因 (Rejection Rationale)**: 违背“确定性锚点”原则，单点依赖大模型自律，导致规范通过率低下。

#### 方案 B: 静态线性流程脚本 (Static Linear Script)
- **核心设想**: 将步骤固定为单一顺序执行的 Bash/Python 脚本。
- **优势 (Pros)**: 实现简单直观。
- **劣势与硬伤 (Cons)**: 无法优雅处理人工评审被拒绝时的返工循环（Rejection Loop），且状态断点恢复极其僵硬。
- **被否决根因 (Rejection Rationale)**: 缺乏分支回退与交互适应能力。

#### 方案 C (采纳方案): 确定性有限状态机 (FSM Orchestrator)
- **核心设想**: 显式定义状态空间（`INIT` -> `GRILLING` -> `GROUNDING` -> `STRUCTURAL_MODELING` -> `CONTRACTS_AND_DECISIONS` -> `DELIVERY_PLANNING` -> `COMPLETED`），每一步跳转强制挂载 Gatekeeper 审计断言。
- **优势 (Pros)**: 状态迁移严格闭合；支持状态快照持久化与随时恢复；天然支持人工拒绝回退。
- **已知劣势与代价 (Cons)**: 增加了状态定义与转移规则的编码维护成本。

## 3. 决策结果与裁决理由 (Decision Outcome & Rationale)

我们决定采纳 **方案 C (确定性有限状态机 FSM)** 作为架构技能全生命周期的核心控制引擎。

### 关键裁决依据 (Decisive Justifications)
1. **坚决落实确定性锚点原则 (Deterministic Anchor Rule)**:
   严禁将流程推进的正确性单点寄托在大模型提示词的自律上。FSM 编排器以宿主 Python 代码形式外置运行，强制校验前置工件后才触发状态跳跃。
2. **供应商中立与极低逆转成本 (Vendor Neutrality Review)**:
   编排逻辑不依赖任何模型厂商的专有 Function Calling 扩展或特定 System Prompt 语法。未来从云端 API 切换为本地开源模型时，FSM 代码零修改，具备很强的抗脆弱性。
3. **消除可观测性黑盒排障成本 (Debuggability Impact)**:
   状态机状态由独立的 `.state.json` 文件持久化管理，任何一步状态流转均可精确映射到前端看板与时序图中，杜绝在杂乱的多轮对话中搜寻当前进度的排障负担。

## 4. 影响、代价与工程缓解策略 (Consequences, Trade-offs & Mitigations)

### 4.1 正向收益 (Positive Consequences)
- **流程规范标准化**: 架构设计各阶段产物井井有条，消除跳步与占位符遗留。
- **可观测与看板化**: 状态机的当前状态与产物集合可直接转化为交互式看板。

### 4.2 负面代价与技术妥协 (Negative Consequences & Trade-offs)
- **代价 1 (灵活性受限)**: 状态机强制单向跃迁，用户无法在未澄清需求的情况下直接生成部署拓扑。
- **代价 2 (黑盒排障与单点状态冲突)**: 若多个并发进程同时写入同一个 `.state.json` 状态文件，可能产生脏写覆盖。

### 4.3 工程缓解与补偿策略 (Mitigations & Compensating Controls)
针对上述每一项负面代价，制定严密的工程兜底防线：
1. **针对 [代价 1] 的缓解 (设计模拟跳板与调试模式)**:
   为熟练用户和自动化测试提供合法的模拟前置产物注入机制，既保合规又保测试效率。
2. **针对 [代价 2] 的缓解 (原子化写入与文件锁)**:
   状态更新采用原子写机制（临时文件写入完毕后执行文件系统原子重命名），消除损坏隐患。
