# ADR-001: 采用基于确定性有限状态机 (FSM) 的架构生命周期编排器

## 元数据 (Metadata)
- **决策编号**: ADR-001
- **状态 (Status)**: 已接受 (Accepted)
- **提出日期 (Date)**: 2026-03-15
- **决策责任人 (Owner / Architect)**: 架构技能核心委员会
- **评审参与人 (Reviewers)**: AI Agent 运行时架构师、软件工程规范负责人
- **涉及组件范围 (Scope)**: `orchestrate_architecture_lifecycle.py`, `Gatekeeper` 校验模块

## 1. 背景与驱动力 (Context & Forces / Drivers)
在复杂软件架构的设计过程中，若允许大语言模型自由发挥、跳步推演或无约束协同，极易产生“跳过非功能性需求直接写代码”、“未定义边界契约直接生成物理模型”、“产出物缺乏一致性校验”等灾难性问题。
系统需要一套既能引导智能体自主推进、又能施加严密工业级门禁（Gatekeeper）与人类干预回退（HITL）的生命周期调度核心。

### 核心矛盾焦点 (Core Conflict)
1. **智能体自主生成效率 vs 工业级架构工程严谨性**: 架构设计必须经历严格的“需求澄清 -> 概念抽象 -> 逻辑解耦 -> 物理运行 -> 决策取舍 -> 交付评估”单向递进链路。
2. **长会话上下文易丢 vs 复杂多步任务断点可恢复性**: 必须支持随时中断、状态落地并在新会话中无缝恢复。

## 2. 考量的备选方案 (Options Considered)

### 2.1 候选方案对比矩阵 (Trade-off Comparison Matrix)

| 评估维度 (Evaluation Criteria) | 方案 A: 纯提示词网状自主智能体 | 方案 B: 静态线性 Shell 脚本 | 方案 C (采纳方案): 确定性有限状态机 (FSM) |
| :--- | :--- | :--- | :--- |
| **执行路径确定性** | 极低 (概率性跳步与循环) | 较高 (严格从头到尾) | **100% 状态机驱动，合法跳转受限** |
| **断点恢复能力** | 差 (依赖上下文窗口注入) | 差 (无细粒度状态持久化) | **原生支持 JSON 状态快照与无缝 Resume** |
| **门禁拦截能力 (Gatekeeping)**| 弱 (容易被 Prompt 绕过) | 中等 (基于简单 exit code) | **强类型硬门禁，产物不达标禁止跳转** |
| **人工介入回退 (HITL)** | 难以精准控制回退步长 | 不支持中断回退 | **支持 REJECT 直接回退至指定澄清状态** |
| **综合裁定** | **否决 (Rejected)** | **否决 (Rejected)** | **采纳 (Accepted)** |

---

### 2.2 各备选方案详细分析

#### 方案 A: 纯提示词驱动的网状自主智能体 (Autonomous Multi-Agent Swarm)
- **核心设想**: 依赖 System Prompt 引导多个 Agent 互相交流自发推进设计。
- **优势 (Pros)**: 灵活性高，前期开发极快。
- **劣势与硬伤 (Cons)**: 执行链路非确定；Agent 常在未收敛需求前直接臆造物理实现；缺乏不可逾越的机器门禁。
- **被否决根因 (Rejection Rationale)**: 无法保证企业级架构规范的百分之百贯彻，被否决。

#### 方案 B: 静态线性流程脚本 (Static Linear Script)
- **核心设想**: 将步骤固定为单一顺序执行的 Bash/Python 脚本。
- **优势 (Pros)**: 实现简单直观。
- **劣势与硬伤 (Cons)**: 无法优雅处理人工评审被拒绝时的返工循环（Rejection Loop），且状态断点恢复极其僵硬。
- **被否决根因 (Rejection Rationale)**: 缺乏分支回退与交互适应能力，被否决。

#### 方案 C (推荐方案): 确定性有限状态机 (FSM Orchestrator)
- **核心设想**: 显式定义状态空间（`INIT` -> `GRILLING` -> `GROUNDING` -> `STRUCTURAL_MODELING` -> `CONTRACTS_AND_DECISIONS` -> `DELIVERY_PLANNING` -> `COMPLETED`），每一步跳转强制挂载 Gatekeeper 审计断言。
- **优势 (Pros)**: 状态迁移严格闭合；支持状态快照持久化与随时恢复；天然支持人工拒绝回退。
- **已知劣势与代价 (Cons)**: 增加了状态定义与转移规则的编码维护成本。

---

## 3. 决策结果与裁决理由 (Decision Outcome & Rationale)

我们决定采纳 **方案 C (确定性有限状态机 FSM)** 作为架构技能全生命周期的核心控制引擎。

### 关键裁决依据 (Decisive Justifications)
1. **不可逾越的质量门禁**: 状态机将规范转化为硬编码校验，产物格式不符或缺少必要字段无法触发状态推进。
2. **无缝断点续接**: 无论何时退出，状态与上下文始终保存在本地，极大提升多轮会话稳定性。

## 4. 影响、代价与工程缓解策略 (Consequences, Trade-offs & Mitigations)

### 4.1 正向收益 (Positive Consequences)
- **流程规范标准化**: 架构设计各阶段产物井井有条，消除跳步与占位符遗留。
- **可观测与看板化**: 状态机的当前状态与产物集合可直接转化为交互式看板。

### 4.2 负面代价与技术妥协 (Negative Consequences & Trade-offs)
- **代价 1 (灵活性受限)**: 用户无法跳过前期需求澄清直接生成部署拓扑。
- **代价 2 (状态文件并发竞争)**: 若多个进程同时修改状态文件可能产生覆盖冲突。

### 4.3 工程缓解与补偿策略 (Mitigations & Compensating Controls)
针对上述每一项负面代价，架构设计中制定了严密的工程兜底防线：
1. **针对 [代价 1] 的缓解 (设计跳过指令与测试跳板)**:
   - 为熟练用户和自动化测试提供合法的模拟前置产物注入机制，既保合规又保效率。
2. **针对 [代价 2] 的缓解 (原子化写入与文件锁)**:
   - 状态更新采用原子写机制（临时文件重命名），消除文件损坏隐患。
