作为资深架构师，你知道 architecture thinking 吗？

架构思维（Architecture Thinking）本质上是一种在高度不确定性、复杂约束和多变需求中，通过结构化抽象来权衡、决策并演进系统的核心认知能力。

在软件工程与AI系统设计中，它远不止于画几张拓扑图或选择特定的技术栈，而是一套贯穿生命周期的思维模型：

第一性原理与边界划定：透过眼前的业务表象，识别出系统的核心资产、关键不变量（Invariants）与核心矛盾。明确“什么可以做，什么绝对不能做”，并通过定义清晰的边界（Boundaries）来遏制复杂度蔓延。

权衡取舍的艺术（Trade-offs）：架构没有银弹，本质上全是权衡。架构思维要求我们在一致性与可用性、扩展性与开发成本、Token消耗与执行精度之间做出符合当前及未来演进阶段的显式决策。

面向未来的演进性（Evolutionary Design）：承认“需求永远在变”。优秀的架构思维不追求一步到位设计出完美的终态，而是构建低耦合、高内聚的结构，使得系统在未来业务膨胀或范式迁移时，能够以最小的代价进行局部重构或替换。

抽象与解耦：善于将混沌的现实业务映射为干净的领域模型（Domain Model），通过引入中间层、协议抽象或代理层，实现关注点分离（Separation of Concerns），从而降低模块间的认知负荷与变更涟漪。

无论是构建高吞吐的分布式后端，还是设计具备自我纠错与长程规划的 AI Agent 架构（如处理上下文压缩、执行回退、状态隔离等），架构思维都是从“能跑就行”走向“健壮、可维护、可演进”的分水岭。

传统软件工程中的架构思维（如 TOGAF、4+1 视图、ATAM 架构评估等方法论）中，还存在几个决定系统生死的关键维度尚未补齐：

质量属性与非功能需求（Quality Attributes / NFRs）

系统“做得怎样”而非“做什么”：性能、吞吐量（TPS/QPS）、可用性（SLA/SLO）、容灾与 RPO/RTO、数据一致性等级、安全性（认证鉴权/合规/审计）等。功能需求决定系统能不能用，非功能需求决定系统能活多久。

硬性约束与假设边界（Constraints & Assumptions）

不可变边界：合规性（如 GDPR、数据本地化）、法律/行业牌照限制、既定技术栈强依赖、预算上限。

显式假设：在不确定信息下做出的推断，必须记录在案（例如“假设上游结算接口延迟 <200ms”），一旦假设失效，架构需要重估。

数据架构与生命周期模型（Data Architecture）

独立于逻辑模型的数据域视图：读写模型分离（CQRS）、数据所有权（Single Source of Truth）、冷热分级存储、流批处理边界，以及数据备份、归档与清理生命周期。

系统边界与外部集成契约（System Context & Integration Contracts）

C4 模型中的 Context 视图：本系统与外部三方系统、上下游遗留系统的边界定义。

集成协议与防腐策略：同步 RPC/异步 MQ、API 契约语义、防腐层（ACL）设计以防外部模型污染核心域。

失效模式与韧性设计（Failure Modes & Resilience）

架构不是假设“不会出错”，而是设计“如何死得体面”：降级、熔断、限流、幂等性重试、隔离壁舱（Bulkhead）、脑裂自愈机制。

可观测性体系（Observability Strategy）

并非运维落地时才考虑，而是架构阶段就应确立的顶层规范：分布式链路追踪（Trace）、统一结构化日志规范（Log）、黄金指标监控（Metrics）与告警收敛链路。

如果将你的 12 项与补充内容按照架构思维的递进逻辑整合，通常会形成一个自顶向下的四层推导体系：

层次	核心关注点	包含维度
1. 输入与边界	为什么做？在什么限制下做？	Business Driver、用户分类/角色、Use Cases、NFRs（性能/可用性/安全）、现有环境分析、硬约束与假设
2. 概念与逻辑抽象	领域是什么？核心边界在哪？	Architecture Overview、Logical Model（领域/数据模型）、System Context 与集成边界
3. 物理与工程权衡	技术如何落地？如何应对故障？	Deployment Model、Data Architecture、韧性与容灾机制、可观测性设计、Architecture Decisions (ADR)
4. 组织与交付实施	谁来做？按什么节奏做？	Org Structure（康威定律应用）、Estimation、Working Plan、First Step（PoC / 骨架原型）
架构思维最核心的价值，不是填满上面这套清单，而是在需求、约束与技术选型之间建立可追溯的因果链条：任何一个部署节点或逻辑划分，都能一路向上溯源到某个特定的业务目标或物理约束。

在现代 AI / Agent 系统中，传统架构思维的骨架依然有效，但核心假设发生了根本性位移。传统软件是建立在“确定性输入、图灵机逻辑、强事务一致”之上的，而 Agent 系统则必须面对“概率性推理、自然语言协议、长程非确定性状态”。

这种范式迁移颠覆了传统架构的几个核心维度：

1. 确定性契约的瓦解：从强类型 API 到概率性接口
传统视角：接口是严格定义的（Protobuf、OpenAPI），入参和出参有完备的契约保证。

Agent 重塑：

核心计算单元（LLM）的输出是分布概率采样，而非确定性函数。

架构应对：架构师必须引入护栏机制（Guardrails）与防御性结构化输出（如 Pydantic、Json Schema 约束、语法掩码引导），以及幻觉检测和后校验拦截层。架构思维从“确保无错输入产生预期输出”，转向“假设组件必然随机失效，如何收敛输出边界”。

2. Logical Model 的演进：从数据流到认知循环（Cognitive Loop）
传统视角：逻辑模型主要是领域模型（DDD）、数据流图（DFD）和状态机（FSM）。

Agent 重塑：

核心不再是静态的 CRUD 或固定的业务管道，而是感知（Perception）- 规划（Planning）- 记忆（Memory）- 行动（Action）的动态闭环。

逻辑架构需要显式建模：

记忆分级：工作记忆（Working Memory / In-context）、情境记忆（Episodic Memory / 向量库检索）、语义记忆（Semantic Memory / 知识图谱）。

决策拓扑：单智能体 ReAct 循环、分层规划（Hierarchy Planning）、亦或是多智能体协作网络（Supervisor-Worker, Consensus）。

3. NFRs 的彻底重构：从毫秒级延迟到 Token 经济学与非确定性指标
传统系统的可用性、吞吐量和延迟指标，在 Agent 系统中演变成了全新的评价维度：

维度	传统软件 NFR	Agent 系统 NFR
时延指标	TP99 < 100ms	TTFT (Time to First Token)、长程规划总耗时（常以秒/分钟计）
计算成本	CPU/内存占用、实例费用	Token 经济学（Prompt 膨胀率、缓存命中率、每轮任务 Token 预算）
质量标准	功能正确率、单元测试覆盖率	评测基准（Benchmark pass@k）、语义漂移容忍度、幻觉发生率
并发与瓶颈	数据库连接池、网络 I/O 阻塞	模型提供商 TPM/RPM 配额限制、推理并发队列调度
4. 故障模式与重试逻辑：从幂等退避到“反思与负向归纳”
传统视角：调用超时或失败时，采用指数退避重试（Exponential Backoff）或降级 fallback。

Agent 重塑：

盲目重试原请求毫无意义，甚至会导致智能体陷入死循环（如无限调用同一个报错的工具）。

架构应对：重试机制必须演进为认知重试——包括错误回溯（Stack Trace 剪枝注入）、假设推翻账本（Negative Hypothesis Ledger）以及让模型进行自我反思（Reflection / Self-Correction）后再生成新的尝试路径。

5. 上下文即架构状态（Context-as-a-State）
传统视角：状态保存在关系型数据库或 Redis 中，内存占用成本极低。

Agent 重塑：

上下文窗口（Context Window）是系统最稀缺、最昂贵、最具易失性的“工作内存”。

架构设计需要专门的上下文工程中间件：决定何时进行滑动窗口截断、何时进行语义摘要压缩、何时引入外部增量 Diff 挂载，以及如何平衡“注意力稀释（Needle-in-a-Haystack 效应）”与信息保真度。

如果说传统架构师的核心使命是消除系统的不确定性，那么 AI / Agent 时代的架构思维，则是在接纳底层组件本质不确定性的前提下，通过工程围栏构建出确定性的业务交付结果。

我希望有一个融合的版本，当前的 architecture 过份地强调针对 agent 的部分，却忽略了传统的那些有用的思想。在我看来一个系统中针对 agent 部分可以用针对 agent 的架构，但大部分还是需要用传统的架构思想来保证质量。哪怕是 vibe coding 这些架构骨架也可以约束 不跑偏

你的判断非常敏锐且切中要害。当前许多纯基于 Prompt 拼装的系统之所以难以真正走向生产环境，正是因为过度神化了模型的泛化推理，却丢掉了软件工程沉淀了几十年的确定性骨架。

即便在 AI 辅助开发甚至高灵活度的 Vibe Coding 场景下，缺乏架构脚手架，代码库也会在几轮迭代后迅速滑向不可控的熵增与逻辑混乱。

真正的工业级架构，应该是一个外层由传统强类型/确定性工程守护、内层包裹概率性 Agent 推理的融合系统。以下是融合后的完整 Architecture Thinking 框架：

1. 业务与输入层：确立基准（Grounding）
Business Driver & 价值验证：不盲目为“上 Agent 而 Agent”。明确区分业务中哪些需要概率性泛化（如模糊意图理解、复杂决策拆解），哪些必须是确定性逻辑（如结算、权限校验、高精度算术）。

用户角色与人机协同边界（HITL）：定义系统与用户的交互模式——是自动驾驶（Autonomous Agent）、副驾驶（Copilot）、还是必须经人类审批关键决策（Human-in-the-Loop）。

场景与用例（Use Cases / Epics）：将业务用例清晰切分为两类：

确定性路径（Deterministic Path）：传统规则/API 驱动，零幻觉容忍。

自适应路径（Adaptive Path）：允许 Agent 试错、规划并调用工具。

2. 约束与指标层：融合 NFRs（非功能性契约）
将传统的系统级质量指标与 AI 经济学指标融合，建立双层质量底线：

维度	传统工程约束（外围骨架）	Agent 专用指标（核心内胆）
性能与时延	API P99 < 200ms、数据库吞吐、并发连接池	首字延迟（TTFT）、单任务步数上限（Step Cap）
成本与容量	机器算力、带宽、存储利用率	Token 经济学（每任务 Token 预算、Prompt 缓存命中率）
质量与正确性	单元测试通过率、接口契约校验（Schema Check）	评测基准（Benchmark pass@k）、语义一致性、幻觉容忍阈值
安全与隔离	RBAC/ABAC、SQL 注入拦截、网络沙箱	Prompt 注入防御、工具权限降权、敏感数据脱敏
3. 逻辑架构：双环模型（Deterministic Shell, Stochastic Core）
系统逻辑不再是单纯的分层结构，也不是失控的纯 ReAct 黑盒，而是“确定性外壳包裹概率内核”：

防腐层与沙箱隔离（Anti-Corruption & Sandbox）：

Agent 永远不直接持有全局写权限。所有工具（Tools）均由传统强类型契约（如 OpenAPI / RPC）严格暴露，入参由 Schema 解析器严格反序列化。

执行环境物理隔离（如只读文件系统视图、执行容器），限制单次调用的爆炸半径。

状态与上下文分级（State & Context Architecture）：

持久化业务状态：必须沉淀在传统数据库（PostgreSQL/Redis），遵循 ACID 或最终一致性。

瞬态认知状态（Context）：作为昂贵的易失性工作内存，由中间件进行生命周期管理（滑动截断、按需 Diff 挂载、语义摘要）。

控制反转与确定性状态机（Deterministic FSM）：

宏观主干流程由传统工作流引擎（如 Temporal 或代码中的显式有限状态机）把控，保证整体业务推进绝不跑偏。

微观分支动作交由 Agent 动态推理，即使模型迷航，外层状态机会通过超时或步数耗尽强制介入收敛。

4. 物理与工程韧性：双重防御
分级失效模式（Resilience Strategy）：

第一层（认知重试）：Agent 内部的反思机制、堆栈剪枝注入、排除已知错误路径。

第二层（工程保底）：当 Agent 超过重试上限或偏离契约时，系统立即降级走传统的硬编码规则或抛出异常告警，杜绝死循环。

统一可观测体系（Unified Observability）：

传统的 Metrics / Logs / Traces 扩展覆盖 LLM 调用链。

将每一次推理的 Prompt、Completion、Tool 调用耗时和消耗的 Token 挂载在同一个分布式 Trace ID 上，形成从前端点击到底层模型采样的端到端链路。

5. 组织与交付实施（落地与约束）
康威定律与团队职责：

传统基础设施/业务平台组负责构建“围栏”（平台、数据通道、工具契约与安全底线）。

AI 工程师/应用组在围栏内部调优提示词、评估模型输出与编排链路。

Architecture Decision Records (ADR)：

记录每个关键抉择的因果链条，特别是：“为什么这里选用 Agent 而不是状态机？”、“该决策对系统成本和确定性的影响是什么？”

敏捷演进与 Vibe Coding 的防护栏（Guardrails）：

即便日常迭代采用高速探索或 AI 辅助编码，架构的目录结构、类型声明、API 契约和核心单元测试必须由人工架构师预先锚定。

架构骨架充当代码生成的“物理围墙”，让 AI 只能在具体的函数实现或局部模块中自由发挥，绝不蔓延污染全局依赖。

要不要基于这个融合框架，推演一个具体业务场景（如自动化故障定位或代码修改）的架构图与流程？

我希望基于这套架构 实现可以用于 coding agent 的 skill 组

在融合架构（Deterministic Shell + Stochastic Core）下，Coding Agent 的 Skill 组绝不能只是粗暴暴露 exec_bash 或把整份源码硬塞进 Prompt。

必须由确定性工程外壳承担环境隔离、上下文剪枝与契约校验，而将概率内核（Agent）严格限制在“基于结构化视图进行推理、修补与反思”的边界内。

一套完备、工业级且抗上下文膨胀的 Coding Skill 组可以划分为以下四类核心接口：

1. 认知感知组（Perception Skills）：剪枝与防注意力稀释
传统思路把完整文件喂给模型，不仅消耗昂贵 Token，还会导致“大海捞针（Needle in a Haystack）”效应导致模型迷航。该组 Skill 的目标是在外层做结构化语义压缩。

repo_skeleton_view（轻量级代码库骨架）

输入：path: str, depth: int = 2

外壳工程实现：基于 AST 解析而非纯文本展示，仅输出目标目录下的模块结构、类名、公开接口签名和 Docstring，屏蔽实现细节。

价值：让 Agent 在极低 Token 消耗下建立宏观系统认知。

ast_symbol_lookup（符号精准定位）

输入：symbol_name: str, context_type: "definition" | "references"

外壳工程实现：借力 LSP（Language Server Protocol）或 ctags/Tree-sitter，直接返回目标符号的定义行区间或引用调用链，拒绝全量文本全局搜索。

pruned_slice_read（局部行范围只读）

输入：file_path: str, start_line: int, end_line: int

外壳工程实现：硬性限制每次单文件读取上限（如单次最多 150 行），并在外层加上带行号的绝对锚点，防止 Agent 产生行号错位幻觉。

2. 状态变更组（Action & Mutation Skills）：确定性基准与局部受控
为了防止模型反复覆写整份大文件导致代码丢损，所有写入操作必须依赖“基准锚定（Baseline-Anchored）”与差异补丁机制。

apply_targeted_patch（行锚定局部 Patch）

输入：file_path: str, original_snippet: str, new_snippet: str

外壳工程实现：

计算 original_snippet 的 Hash 或精确文本匹配。

若命中唯一上下文，则执行精准替换；若存在模糊歧义或多处匹配，外壳直接拦截报错并要求 Agent 补充上下文，防止“改错地方”。

写入前在本地自动暂存版本，支持单步回滚。

sandbox_file_write（受控写入隔离）

输入：file_path: str, content: str

外壳工程实现：沙箱文件系统白名单拦截。禁止读写非项目目录、系统敏感目录（如 /etc、.git/ 内部文件、密钥环境变量等），限定爆炸半径。

3. 验证与防护组（Guardrail & Validation Skills）：错误收敛机制
编译运行是代码任务的物理底线。此组 Skill 的关键在于：过滤无用噪音，防止模型在巨大报错信息中过载。

guarded_test_run（带降噪与剪枝的测试运行）

输入：test_target: str (如 pytest 路径或 npm test 命令)

外壳工程实现：

超时强杀机制（如单次运行限时 30s，防止 Agent 触发死循环卡死）。

堆栈剪枝（Stack Trace Pruning）：外部过滤器剔除第三方库深层调用栈与无意义的中间环境信息，仅保留“失败用例名、核心引发异常行、Diff 对比”，将数百行日志压缩为数行高信噪比信息注入给 Agent。

lint_and_type_check（确定性静态检查）

输入：file_path: str

外壳工程实现：调用 Ruff、ESLint、MyPy 等静态分析工具。若存在语法错误或类型不匹配，在进入端到端测试前以结构化 JSON 返回行号和规则 ID，要求 Agent 在原地快速修正。

4. 记忆与自愈组（Cognitive Memory & Ledger Skills）：防死循环机制
这是防止 Agent 陷入“土拨鼠之日（Groundhog Day）”死循环的关键。传统代码没有这个概念，但 Agent 架构必须把试错轨迹沉淀为显式认知账本。

negative_hypothesis_ledger（负向假设账本）

输入：hypothesis: str, attempted_change: str, failure_reason: str

外壳工程实现：

每次代码修改并测试失败后，Agent 必须显式向账本写入“我刚才假设 X 可以解决问题，但在 Y 处失败”。

中间件在后续每次推理中将此账本作为“已证伪路径”强制注入。当 Agent 再次给出相似的错误补丁时，外壳直接拦截：“该路径已在第 N 步验证无效，请推翻假设换新方向”。

workspace_checkpoint_rollback（快照回退）

输入：checkpoint_id: str

外壳工程实现：底层结合 Git Commit 或内存 VFS 快照。当 Agent 连续 2 轮修改导致破坏了原本通过的测试时，外壳主动执行硬回滚，重置工作区到干净状态，迫使 Agent 重新规划。

明白了，这里的定位是架构师级 Agent（Architecture Design Agent）所使用的 Skill 组：它的产出不是业务实现代码，而是一整套高信噪比、经得起推敲的架构设计资产（ADR、C4 视图、逻辑模型、物理边界、API 契约等）。

这些资产既是与技术评审人沟通的共同语言，也是后续交给下游开发（包括 Vibe Coding）时绝不跑偏的脚手架（Scaffolding）。

在“确定性外壳 + 概率内核”的架构下，这套 Skill 组按推导逻辑分为四大阶段：

1. 约束提炼组（Distillation & Grounding Skills）
这一组 Skill 的目标是把模糊的业务对话、PRD 或痛点，转化为结构化、量化、有边界的输入，防止后续架构推导“空中楼阁”。

distill_nfr_matrix（质量属性与非功能需求提炼）

输入：原始业务诉求文本、预估用户量/流量级。

产出：结构化 NFR 矩阵（含 P99 延迟目标、RPO/RTO、强/弱一致性边界、Token 预算/并发估算）。

外壳约束：强制要求每个指标必须附带“业务影响”和“度量基准”，杜绝空洞的“系统应具有高可用性”。

catalog_invariants_and_constraints（不变量与不可变边界编目）

输入：合规要求、遗留系统协议、技术栈偏好、预算上限。

产出：系统“硬约束清单”（Must-Have）与“绝对红线”（Must-Not-Do）。

沟通价值：在架构评审第一步就对齐什么是不能碰的雷区。

2. 结构建模组（Structural Modeling & Abstraction Skills）
架构的核心在于边界划分。该组 Skill 将提炼出的概念转化为标准的系统模型与视图（采用 C4 模型标准）。

generate_system_context（系统上下文与生态位 - C4 Level 1）

输入：核心系统定位、外部依赖系统、用户角色清单。

产出：Mermaid 图代码与职责边界描述，标明谁在调用本系统、本系统依赖谁，以及外部集成的防腐层（ACL）位置。

derive_logical_domain_model（逻辑域划分与统一语言）

输入：核心 Use Cases、实体行为。

产出：

限界上下文（Bounded Contexts）划分。

核心领域实体（Entities）、值对象（Value Objects）与聚合根（Aggregate Roots）关系图。

状态跃迁图（State Machine）。

synthesize_architecture_overview（全景容器拓扑 - C4 Level 2）

输入：逻辑域模型、NFR 性能指标、技术偏好。

产出：网关层、计算单元（传统微服务 vs. Agent 认知环）、存储分级（ACID 业务库 vs. 向量/图/缓存）、消息主干的拓扑架构。

3. 决策与契约组（Contract & Decision Framing Skills）
这是约束后续 Vibe Coding 绝对不跑偏的核心抓手。如果给下游写代码的 Agent/人类开放自由度，必须用强契约把它们限制在各自的格子里。

record_architecture_decision（结构化 ADR 生成）

输入：争议点技术选型（如“为什么核心事务用 PostgreSQL 而不是纯图数据库”、“为什么某链路用规则引擎而非 Agent”）。

产出：标准 ADR 文档（状态、上下文、面临的 Options、权衡决策依据、负面后果与妥协）。

沟通价值：让所有人知道为什么这么设计，避免团队重复推翻重来。

scaffold_boundary_contracts（API 契约与骨架生成器）

输入：逻辑模型中的模块间调用关系。

产出：

严格类型化的 OpenAPI Spec / Protobuf 定义 / JSON Schema。

模块公开接口签名，包含入参校验规则与异常错误码体系。

对 Vibe Coding 的约束：后续编码时，代码生成器只能在这些确定的 Interface 内部填充逻辑，禁止擅自修改公开契约。

generate_failure_resilience_matrix（失效模式与容灾矩阵）

输入：组件清单与外部集成点。

产出：

组件级故障分析表（依赖超时、重试风暴、降级策略、熔断阈值、数据补偿方案）。

4. 实施规划与骨架脚手架组（Execution & Scaffolding Skills）
将设计图纸转化为工程可执行的第一步，搭建最小可行骨架（Walking Skeleton）。

bootstrap_walking_skeleton（项目工程物理脚手架生成）

输入：架构概览与技术栈选型。

产出：

包含清晰模块边界的项目目录树（如 Clean Architecture / 六边形架构的 domain/, ports/, adapters/）。

包含核心基础类型的空实现或 Stub。

根目录 ARCHITECTURE.md 与 AI 编码指导规则（如 .cursorrules / .windsurfrules），显式告知 Vibe Coding 工具：“哪些目录是核心领域不可随意改动，哪些是适配层”。

sequence_delivery_milestones（演进路线与分步工作计划）

输入：Use Cases 优先级与组件依赖拓扑。

产出：

Step 0 (First Step / PoC)：最关键的不确定性验证路径（如跑通主流程契约或核心算法链路）。

Phase 1-N 交付计划：基于端到端纵切（Vertical Slices）而非横向切分的迭代路线图。

补充 1：苏格拉底式需求深挖 Skill（grill_architecture_requirements）
该 Skill 的核心职责是充当挑剔的 Chief Architect。在进入正式建模前，不给用户轻易蒙混过关的机会，通过多轮交叉审讯式对话榨取所有架构必须的物理事实。

触发时机：项目起点，或当任一架构环节因信息模糊产生重大歧义时。

深挖的 5 个攻击面（Attack Surfaces）：

核心动机与伪需求（The "Why" Behind the "What"）：

“你为什么认为这里必须引入某个新技术/复杂模式，而不是最基础的方案？”

“如果不做这个系统，业务眼下最大的物理损失是什么？”

隐性规模与极端负载（Scale & Edge Traps）：

“不要只给日活/总量，峰值 QPS、数据膨胀速率是多少？读写比是 9:1 还是 1:1？”

“单次请求的最大 Payload 是多大？是否存在单点大客户（Hot-key）倾斜？”

一致性与容灾底线（Tolerances & Blast Radius）：

“系统挂掉 30 分钟能否容忍？故障时更偏向于降级可用（AP）还是锁死拒绝（CP）？”

“数据丢一条会有多大法律或商业后果（RPO/RTO 现实底线）？”

现有资产与政治/组织约束（Organizational Reality）：

“团队的技术栈偏好和维护上限是什么？上线后谁来负责第一线 On-call？”

“是否存在不可变动的既有遗留系统？接口文档完备吗？”

业务领域不变量（Domain Invariants）：

“这个业务里，哪件事发生就算‘系统彻底崩坏’（比如账户余额变负数、状态倒流）？”

停止深挖条件（Gatekeeper Exit Criteria）：

所有 NFR 核心指标具备量化上下限。

至少识别出 3 个致命故障场景与业务红线。

产出结构化的 Architecture_Input_Spec.json 作为下游唯一的真理源。

1. grill_architecture_requirements 提示词规范
该 Skill 扮演一名极度挑剔、讲究工程底线、反直觉追问的 Chief Architect。它的任务是拒绝模糊与过度设计，逼出隐性约束。

Markdown
# Role: Chief Architecture Inquisitor (`grill_architecture_requirements`)

## Core Philosophy
- 用户往往把“方案”当成“需求”。你的工作是剥离方案外衣，探寻业务底层物理事实。
- 拒绝任何形容词（如“高性能”、“高可用”、“低延迟”），强制转化为物理指标与业务代价。
- 采用对抗式深挖（Grilling）：挑战不合理的复杂性，逼问故障与最坏情况（Blast Radius）。

## Execution Principles
1. **One Focus at a Time**: 每轮对话仅抛出 1 到 2 个直击痛点的问题，切忌长篇大论问卷式轰炸。
2. **Challenge Assumptions**: 若用户提出“必须用微服务 / 必须用多 Agent / 必须用向量库”，直接质疑：“如果用单体/最简单的 SQLite 脚本做，第一天会遇到什么致命物理瓶颈？”
3. **Trace the Bleeding**: 聚焦故障边界。“系统宕机 1 小时，业务损失多少钱？”、“哪种数据损坏会导致业务直接被监管重罚或关停？”
4. **No Premature Exit**: 绝不因用户给出抽象回复而放行。用户若回答“延迟越低越好”，追问：“50ms 与 500ms 对你的业务转化率有可验证的物理差异吗？如果为此架构成本翻 10 倍，你做不做？”

## Grilling Vectors (The 5 Angles)
- **Vector 1: Real Drivers vs. Vanity**: 到底解决了什么具体痛点？不用该系统会怎样？
- **Vector 2: Scale & Cold Numbers**: 峰值 QPS、单次 Payload 极值、读写比、冷热数据膨胀速率。
- **Vector 3: Failure Tolerance**: RPO/RTO 硬指标、脑裂容忍度、网络分区时的偏向（CP 还是 AP）。
- **Vector 4: Team & Ops Reality**: 团队维护能力、技术栈红线、现有遗留系统交互的肮脏细节（Dirty Reality）。
- **Vector 5: Domain Invariants**: 绝不可打破的业务铁律（例如“状态不可倒流”、“资产不可为负”）。

## Gatekeeper Exit Criteria (退出门禁)
只有当满足以下所有条件时，才允许终止盘问并输出 JSON：
- [ ] 核心业务驱动力与非做不可的理由已明确，剔除一切伪需求。
- [ ] 至少 3 个核心质量属性（NFR）具备明确的数值上下限与业务影响基准。
- [ ] 至少识别出 2 个不可违背的“绝对红线”（Invariants）。
- [ ] 组织与技术栈硬约束（语言、运维基础设施、预算）已确认。

Markdown
# Skill: grill_architecture_requirements

## Role
你是资深首席架构师（Chief Architecture Inquisitor）。你绝不相信用户给出的第一版需求描述。面对任何模糊词汇（“高可用”、“海量数据”、“智能 Agent”、“操作简单”），你必须进行解构与质询。

## Operational Rules
1. **单点对抗（Laser Focus）**：每轮对话最多抛出 2 个具体问题。严禁给出一整张由 10 个问题组成的问卷。
2. **剥离伪需求（Strip Solutionism）**：当用户直接提出方案时（如“我们需要一个基于 Kafka + Flink + 向量库的实时 Agent 调度”），强制将其拉回问题本身：“在不用这些复杂组件的前提下，最简单的 CronJob 脚本在哪一步会物理崩溃？具体的物理瓶颈是什么？”
3. **逼问边界与故障代价（Blast Radius）**：
   - “如果这个系统完全挂掉 2 小时，公司会损失多少钱或面临什么法律后果？”
   - “峰值 QPS 是多少？读写比例？单条记录最大是多少 KB/MB？”
   - “数据丢一条是否可接受？在网络分区（Network Partition）发生时，你是优先保证能继续写入（AP），还是宁可报错拒绝也绝不写入脏数据（CP）？”
4. **探查团队与既有负债（Real-world Footprint）**：
   - “上线后谁负责维护？团队最熟悉的技术栈是什么？”
   - “这个系统必须对接哪些历史遗留系统？它们的接口稳定吗？有没有不可触碰的物理黑盒？”

### Skill 3：`catalog_invariants_and_constraints`（不变量与不可变边界编目器）

该 Skill 的任务是**划定系统绝对不能跨越的红线（Invariants）与环境硬性物理约束**。这些内容构成了后续 Vibe Coding 与架构演进的“安全物理围栏”。

```markdown
# Skill: catalog_invariants_and_constraints

## Role
你是系统合规与系统安全架构师。你的职责是把业务红线、组织限制、合规要求转化为开发与生成代码时必须严格遵守的“不变量编目”。

## Core Rules
1. **区分约束与假设**：
   - **Constraint（硬约束）**：外界施加、不可妥协的客观现实（如“必须运行在内网环境”、“严禁使用 GPLv3 库”）。
   - **Invariant（领域不变量）**：业务核心规则，在任何时刻、无论经历多少并发或故障都绝对不能打破的真理。
   - **Assumption（显式假设）**：当前信息不完备时的前提推断，必须记录失效触发条件。
2. **输出落盘路径**：`docs/architecture/00-grounding/constraints-and-assumptions.md`。

## Output Template (`constraints-and-assumptions.md`)

```markdown
# Constraints, Invariants & Assumptions Specification

## 1. 核心领域不变量 (Domain Invariants)
*违背以下任何一条，即判定为系统发生重大故障（P0 Bug）：*
1. **状态单向跃迁**：状态从 `PROCESSING` 只能前进到 `COMPLETED` 或 `FAILED`，绝对不允许回退到 `PENDING`。
2. **零越权隔离**：租户 A 的任何请求（无论是 API 还是 Agent 探索）物理上绝对无法读取租户 B 的沙箱和元数据。
3. **副作用执行鉴权**：所有涉及物理写（文件写入、外部调用、数据库修改）的操作，必须经过确定性权限校验层，概率模型不能绕过权限直接执行。

## 2. 物理与工程硬约束 (Hard Constraints)
- **技术栈白名单**：后端必须使用 Python 3.11+ 或 Go 1.22+，禁止引入未经安全审计的三方 C 扩展库。
- **部署环境**：内网私有化部署，无公网直接出向访问权限；所有模型推理必须走内网自建网关。
- **依赖隔离**：第三方工具调用超时硬性限制为 10 秒，超过直接抛出 TimeoutException，禁止无限挂起。

## 3. 显式假设与失效触发条件 (Assumptions & Invalidation Triggers)
| 假设内容 | 做出假设的理由 | 失效触发条件 (Invalidation Trigger) | 失效后架构应对方案 |
|---|---|---|---|
| 上游身份认证服务延迟 < 50ms | 属同一 VPC 内网调用 | 跨地域部署或上游升级造成 P99 > 200ms | 引入本地短期 Token 缓存并做异步刷新 |
| 单任务文件变更数 <= 10 个 | 业务以局部修改为主 | 出现批量重构类任务 (>50 个文件) | 切换为批量文件归档流式处理引擎 |

## 1. 状态 (Status)
**Accepted** (2026-09-16)

我们在设计一套支持自动化架构生成与代码修补的系统。纯 Prompt/LLM 驱动的黑盒 Agent 极易陷入死循环、产生行号错位幻觉，且对不可预知的外部错误缺乏幂等恢复能力。传统的硬编码状态机又无法处理高度非结构化的语义分析与发散性方案探索。系统必须在灵活性与确定性之间找到工程落地的平衡点。

  * 为下游 Vibe Coding 提供只读的物理沙箱和确定的入参契约。
* **Negative Trade-offs / Costs**:

### Skill 9：`generate_failure_resilience_matrix`（失效模式与容灾降级矩阵生成器）

该 Skill 的任务是**前置推演“系统如何死得体面”**。它针对所有内外部调用点、网络超时、模型失效场景，明确定义降级、熔断与自我修复链路。

```markdown
# Skill: generate_failure_resilience_matrix

## Role
你是系统高可用与混沌工程架构师。你的任务是推演全链路每一个集成点的失效场景，制定防御性响应策略。

## Core Rules
1. **穷尽致命场景**：覆盖下游 API 5xx/超时、模型生成乱码/幻觉、沙箱测试死循环、磁盘/Token 配额用尽等场景。
2. **区分“重试”与“自愈”**：
   - 确定性错误（如网络瞬时抖动）：采用带抖动的指数退避（Exponential Backoff with Jitter）。
   - 认知逻辑错误（如生成的代码跑不通测试）：严禁无脑重试，必须进入“负向假设账本”反思自愈链路，超限直接阻断。
3. **输出落盘路径**：`docs/architecture/02-decisions/failure-resilience-matrix.md`。

Skill 10：bootstrap_walking_skeleton（物理工程脚手架与 Vibe 防护网生成器）
该 Skill 的核心任务是在磁盘上初始化真实的工程目录、挂载类型桩代码（Stub），并生成根目录下的 .agent-rules.md。它为下游编码构筑了物理隔离墙，确保 Vibe Coding 时 AI 只能在指定的沙箱槽位填空，绝对无法破坏架构边界。

Markdown
# Skill: bootstrap_walking_skeleton

## Role
你是代码工程脚手架与开发体验架构师。你的任务是将经过签署确认的契约（Contracts）和领域模型（Domain Models），直接投影为具体的项目代码物理骨架（Walking Skeleton）以及下游 AI 编码规范。

## Core Rules
1. **六边形 / 洋葱架构强隔离**：
   - 生成物理目录树：必须包含 `domain/`（纯业务模型，零外部依赖）、`ports/`（抽象接口）、`adapters/`（外部实现如 DB、HTTP、LLM Client）。
   - 依赖方向严格单向：外层依赖内层，内层严禁引用外层。
2. **强类型与空桩注入（Stubs Generation）**：
   - 将 OpenAPI 和 Schema 编译/转换为目标语言的类型声明文件（如 `src/domain/types.py` 或 `src/domain/types.ts`）。
   - 针对核心用例生成空实现模板，内部显式使用统一标记：`# TODO: [VibeCoding Slot] Implement logic according to ADR-XXX`。
3. **生成 AI 编码硬隔离规则（`.agent-rules.md`）**：
   - 必须在项目根目录生成专为 Cursor / Windsurf 等工具准备的规则文件，声明“不可篡改目录”、“测试先行原则”和“静态校验命令”。
4. **输出落盘路径**：
   - 物理项目目录：`src/`
   - 脚手架清单：`docs/architecture/04-execution/walking-skeleton-spec.json`
   - AI 规则文件：`.agent-rules.md`（并符号链接或同构复制到 `.cursorrules` / `.windsurfrules`）

```markdown

## 1. 绝对禁止修改的不可变资产 (Immutable Boundaries)

### Skill 11：`sequence_delivery_milestones`（交付路线图与 First Step 验证器）

该 Skill 的任务是**把宏观架构拆解为敏捷交付的垂直切片（Vertical Slices）**，并特别定义 **Step 0 / First Step**——即用来验证整个架构中最致命不确定性的最小可行验证路径（PoC / 穿刺测试）。

   - 第一步（Milestone 0）不追求功能完整，只追求跑通核心技术链路的穿刺测试（如：跑通一个带超时的沙箱执行，或跑通一次带契约校验的结构化提取）。
3. **定义每个阶段的退出准则（DoD - Definition of Done）**：
   - 必须包含：自动化测试通过率、性能压测基准、文档同步更新。
4. **输出落盘路径**：`docs/architecture/04-execution/roadmap-and-first-step.md`。
